# Working on MC-707 Toolbox

This is the guide for anyone changing the code, people and coding agents alike. Read it first.
`docs/ARCHITECTURE.md` explains how the parts fit, and has a one-line description of every
module.

## What this is

A song arranger and live performance tool for the Roland MC-707 (and MC-101). It sends MIDI to
the hardware over USB from the browser (Web MIDI) or from a small Windows app (Electron). The
code is plain JavaScript ES modules in `src/`, with no framework and no runtime dependencies
apart from `lamejs` for MP3.

## Commands

```
npm run tools      once: installs esbuild, Prettier and Playwright into .ci-tools/ (kept out of the app's packages)
npm run dev        serve src/ at http://localhost:8707 (Chrome or Edge); edit a file, reload the page
npm run build      build the single-file app: index.html at the repo root
npm test           the full test suite on the built index.html (about 2 minutes)
npm run check      index.html is up to date, and the modules follow the layer rules
npm run format     Prettier on src/, scripts/ and tests/
npm start          run the Windows app (Electron) from the repo (after npm install)
```

To test the source as it is, without building: start `npm run dev`, then run
`APP_URL=http://localhost:8707 npm test`.

## Where things are

```
src/
  index.html        markup only
  main.js           start-up: module load order, hooks, boot
  styles/           CSS, loaded in the order index.html lists them
  core/             helpers, theory, device, the song state S, song model, hooks, types
  library/          the factory pattern library and pattern pools
  services/         MIDI, transport (the clock), preview synth, audio, clip switching, CC automation
  clips/            the "Your MC-707 clips" screen and clip chips
  song/             Song Mode: arrangement, pattern editor, library panel, wizard, export, recording
  live/             Live Mode: engine, scenes, cues, moves, breaks, pads, Raven mode, controller keyboard
  zen/              the ZenCore editor: MC-707 SysEx, tone and kit parameter tables, MFX types, editor pages
  ui/               the app shell: menu bar, toolbar and shortcuts, projects, menus, dialogs, grabber
scripts/            build, dev server, import-layer check, module-map generator
tests/              Playwright tests, baselines (expected output) and fixtures (saved data from v0.10.0)
docs/               ARCHITECTURE.md, screenshots and feature cards for the README
index.html          GENERATED by npm run build; never edit it
```

Each module starts with a header: what it does, which shared state it owns, and which it reads.
To find code, read the module map in `docs/ARCHITECTURE.md`, or search the headers:
`grep -rn "^// " src --include=*.js | head -400`.

## Rules

1. **Never edit `index.html` at the repo root.** Change `src/`, then `npm run build`. CI fails if
   the two differ.
2. **Imports only point down the layers:** core → library → services → clips → song, live
   and zen → ui and main.js. Song, Live and zen never import each other. A call that has to point up goes
   through `core/hooks.js`; add it there and fill it in `main.js`. `npm run check` enforces this.
3. **Never change a factory pattern's id**, or the order the library is generated in. Saved songs
   and Live scenes refer to patterns by id. Add new patterns at the end of a generator, with a new
   id prefix.
4. **Never rename a localStorage key or change a saved data shape** without a migration in
   `fixState()` (songs) or the loader that reads it. `tests/fixtures` holds real saves that must
   keep loading.
5. **Song changes:** call `pushUndo()` before changing `S` and `scheduleSave()` after. Replace the
   whole song only with `replaceState()`. Never assign `S` yourself.
6. **One owner per piece of state.** Read state through imports. Change it where its owner allows
   it, and keep new state in the module that owns that feature.
7. **No work when a module loads.** Export functions and constants. Anything that touches the page
   goes in an `init…()` that `main.js` calls.
8. **Keep modules small and named for what they do.** New modules: under about 400 lines, with a
   header comment like the others. New functions: under about 60 lines. Some older functions are
   much longer (see Known debt). Split them when you work on them, not in passing.
9. **Run the tests before committing.** If a baseline test fails because you meant to change
   that behaviour, re-run it with `UPDATE_BASELINES=1`, check the diff in `tests/baselines/`, and
   say why in the commit.
10. **Update the docs with the code.** A new module needs a header; then run
    `node scripts/module-map.mjs` (CI checks the map is current). Update `README.md` for anything
    a user would notice.

## Things that are easy to get wrong

- **Time units.** Bars for clip positions, steps (16 per bar) for notes, ticks (32 per bar) for
  the clock. MIDI and audio times are AudioContext seconds (`AU.ctx.currentTime`), not
  `performance.now()`.
- **`S` is a live binding.** After `replaceState()` every module sees the new song, but an object
  you took from the old `S` (a clip, a track) belongs to the old song.
- **Live Mode uses `Math.random`** for swaps, fills and breaks. The tests replace it with a seeded
  generator, so a new random call changes the Live MIDI baseline even if nothing else changed.
- **Tracks.** There are always 8 in `S.tracks`. The MC-101 uses 4 of them; check `devOn(t)`
  before sending to a track.
- **Track setup.** Don't assume tracks 0-2 are drums and 3-7 are bass…pluck. A track's job comes
  from its role (`core/tracks.js`): use `slotOf(t)` for its job, `trackOf(slot)`/`tracksOf(slot)`
  for the track(s) doing a job (they can be -1 or empty), `poolOf(t)` for its pattern pool and
  `S.tracks[t].type` for drum or tone. The role is saved as an optional `role` field on a track,
  left out for the default layout, so old saves and the baselines are unchanged.
- **Drum tracks send drum lanes, not notes.** A drum note's `n` is a lane 0-11, mapped to MIDI
  through `S.drumMap`.
- **The built file must work from `file://`.** It runs double-clicked from a folder and inside the
  claude.ai page, so it cannot load other files at run time.

## Known debt

- A few very long functions: `renderAudio` (song/audio-dialog.js, about 770 lines), `liveInit`
  (live/ui.js, about 660), `renderEdHead` (song/editor-head.js, about 420), `wizStep3`, and
  `renderLibrary`. Split them when you next change them.
- Many short historic names (`lvBT`, `lvEmute`, `cmFix`, `S`, `LV`). Rename one when you are working in its
  module anyway, in its own commit.
- Modules inside `song/`, `live/` and `ui/` call each other in cycles. That is allowed inside one
  folder, but new code should avoid adding to it.
- The pattern library files (`library/generate.js`, `variety.js`, `factory.js`) are large because
  they are mostly data. Leave their order alone (rule 3).
